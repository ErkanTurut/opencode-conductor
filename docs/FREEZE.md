# Supervisor Freeze

`tools/opencode-supervisor` is the pre-port implementation. From the
`p0-freeze-supervisor-tree` task until `p4-saul-switch` lands, it is **frozen**:
no edits, no formatting runs, no generated artifacts committed. It is the
reference the ported `tools/opencode-conductor` package is compared against, and
the tree the runtime can be rolled back to with a single import change.

Two gates enforce this:

| Gate | Command | Checks |
| --- | --- | --- |
| Byte identity | `bun tools/opencode-conductor/scripts/freeze/assert-supervisor-frozen.ts` | every tracked file matches `docs/freeze/supervisor-freeze.json` |
| Behaviour parity | `cd tools/opencode-conductor && bun test tests/parity` | the frozen suite and the conductor suite both pass; conductor has at least as many passing tests |

Both are part of normal test runs (`bun test` in the conductor package), so a
drift or a parity regression fails the suite before it can be committed.

---

## The manifest

`docs/freeze/supervisor-freeze.json` is generated by
`scripts/freeze/manifest.ts`:

```json
{
  "generatedAt": "…",
  "root": "tools/opencode-supervisor",
  "files": { "<repo-relative path>": "<sha256 of file bytes>" },
  "treeHash": "<sha256>"
}
```

- `files` is sorted by relative posix path; `treeHash` is the sha256 of the
  sorted `<path>:<hash>` lines joined with `\n` (no trailing newline).
- `root` is the only location-bearing field and it is repo-relative, so the
  manifest is identical in a checkout, a linked worktree, or a CI clone.
  `generatedAt` is metadata only — it is never hashed.
- Relative paths are resolved against the repo root (`<repo>/tools/…`), not the
  conductor package, so the manifest describes the repository, not a package
  install location.

### Deliberate exclusions

Generated or ignored artifacts are not frozen, because their bytes depend on
the machine rather than on review:

- `node_modules/` — at any depth (dependencies come from `package.json`).
- `dist/` — at any depth (build output; `bun run build` reproduces it).
- `bun.lock` — regenerated by `bun install`.

Non-regular entries (symlinks, sockets) are skipped. That direction is safe: if
a tracked file is replaced by a symlink, the path disappears from the scan and
the check reports a **removal** rather than passing silently.

Everything else in the tree is frozen, including `package.json`,
`tsconfig.json`, `config/`, `profiles/`, `prompts/`, `schemas/`, `docs/`, `src/`,
and `tests/`.

### Verifying and reading the result

```bash
bun tools/opencode-conductor/scripts/freeze/assert-supervisor-frozen.ts
```

- exit `0` — prints `FREEZE_OK <treeHash>`; the tree is byte-identical.
- exit `1` — prints `FREEZE_DRIFT`, then one line per path:
  `+ added`, `- removed`, `~ changed`, plus the expected and on-disk tree hashes.
- exit `2` — the manifest or the tree could not be read (missing, corrupt,
  malformed). This is an operational error, not a statement about drift.

`scripts/freeze/manifest.ts` runs the same check with richer options and prints
the same tokens. `--root <dir>` (or `SUPERVISOR_FREEZE_ROOT`) points the check at
a copy; `--manifest <file>` (or `SUPERVISOR_FREEZE_MANIFEST`) points at an
alternate manifest. Alternate roots exist to audit a copy or rehearse a
re-freeze — **never** use one to claim the real tree matches.

## Behaviour parity

`tests/parity/parity.test.ts` spawns `bun test` in both packages and compares
the Bun summaries. It asserts:

- the frozen suite exits 0 with `0 fail` (currently 406 passing tests),
- the conductor suite exits 0 with `0 fail`,
- `conductor_pass >= frozen_pass` — the conductor package legitimately has more
  tests (`tests/runtime/`, this parity harness), never fewer.

When `tools/opencode-supervisor` is absent (the package extracted or published
standalone) the test **skips** instead of failing, so the package stays
self-contained. Parity is only provable from a repo checkout.

A nested-run guard (`CONDUCTOR_PARITY_CHILD`) stops the spawned conductor suite
from recursively spawning itself.

## Rollback procedure

### Today (before `p4-saul-switch`)

`.opencode/plugins/supervisor.js` still imports the frozen tree:

```ts
import plugin from '../../tools/opencode-supervisor/src/plugin.ts'
```

The conductor package is not on the runtime path yet, so "roll back" is a
**no-op today**: the frozen code is already what runs. If a conductor-side
change misbehaves before the switch, do not touch the frozen tree — leave the
conductor package unreferenced or revert the conductor change. Runtime
behaviour cannot regress from the port until the import moves.

### After `p4-saul-switch`

1. Restore the shim's import to the frozen tree (the line above) and remove any
   conductor-specific re-export added during the switch.
2. Restart opencode. Plugin modules are loaded once at startup; a reload is
   required for the import to take effect.
3. Confirm the reference tree is intact:

   ```bash
   bun tools/opencode-conductor/scripts/freeze/assert-supervisor-frozen.ts   # FREEZE_OK
   cd tools/opencode-supervisor && bun test                                  # 406 pass
   ```

4. If the switch also changed state layout or on-disk formats, roll those
   forward explicitly — the freeze restores **code**, not data written by new
   code. Record any such step in the `p4-saul-switch` rollback notes.

Restoring the shim restores pre-switch behaviour because the frozen tree never
moved: the manifest proves its bytes are the ones that shipped before the
switch.

## Re-freezing deliberately

```bash
bun tools/opencode-conductor/scripts/freeze/manifest.ts --update
```

This rewrites `docs/freeze/supervisor-freeze.json` from the on-disk tree and
must be committed together with whatever changed. When the tree has not changed,
`--update` is a byte-identical no-op (the previous `generatedAt` is preserved),
so an accidental run produces no diff.

**Never re-freeze during a run.** A supervisor run — especially an unattended
one — reasons about the code that started it and emits receipts against it.
Re-freezing mid-run would let the reference tree change under a live run and
silently bless the drift, invalidating the parity baseline and making a later
rollback unverifiable. Re-freeze only:

- on a clean worktree,
- between runs (no supervisor process, no in-flight task lease),
- after reviewing the `FREEZE_DRIFT` diff,
- in the same commit as the change, with the parity suite run before commit.

If drift appears and no re-freeze is intended, treat it as an incident: find the
write that touched the tree, revert it, and re-run the gate until it prints
`FREEZE_OK`.
